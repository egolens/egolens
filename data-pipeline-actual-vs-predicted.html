🔴 Finding 1: subarray().buffer wastes 2.16 GB

Root cause: In convertRangeImageToPointCloud(), new Float32Array(maxPoints × POINT_STRIDE) allocates the maximum capacity, then output.subarray(0, pointCount × POINT_STRIDE) references only the valid portion, but when transferring cloud.positions.buffer, the entire underlying ArrayBuffer is transferred. One-line fix: rangeImage.ts: create a trimmed copy just before returning:
const trimmed = new Float32Array(output.buffer, 0, pointCount * POINT_STRIDE) → const trimmed = output.slice(0, pointCount * POINT_STRIDE)
This reduces wasted memory from 2.16 GB → 0. Expected steady state: 3.29 GB → ~1.1 GB.

⚠️ Finding 2: performance.memory does not work in workers

All worker snapshots report 0 B. performance.memory is a Chrome API available only on the main thread. In a Web Worker, it returns undefined, falling back to 0. Actual worker memory (~100–160 MB/worker during BROTLI decompression) cannot be measured with this API.

🛠 Proposed fix: Float32Array.slice() saves 2.16 GB

rangeImage.ts: convertRangeImageToPointCloud(), final section:

Current (subarray, shared buffer):
const positions = output.subarray(0, pointCount * POINT_STRIDE)

Fix (slice, independent copy):
const positions = output.slice(0, pointCount * POINT_STRIDE)

Effect: Creates a new Float32Array containing only valid points. The original maxPoints array becomes eligible for GC.
The worker briefly holds both the original and the copy; after transfer, the original can be released.
Expected savings: 3.29 GB → ~1.1 GB (−2.16 GB, −66%)
Measured with Chrome performance.memory API · --enable-precise-memory-info flag recommended for higher accuracy
